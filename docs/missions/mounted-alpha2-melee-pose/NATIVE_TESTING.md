# Bounded native testing and disposable fixtures

## Purpose and scope

This mission delivers a reviewed private alpha. Native work is useful for discriminating these bugs, but an absent desktop tool or safe fixture route does not turn the task back into the previous historical-save recovery project. Full visual/gameplay/save-load acceptance remains owner-pending where unperformed.

Begin with a brief read-only capability and safety check: actual callable desktop/game controls, installed game/DLC, current UMM/mod package, usable guarded launch route, shared runtime claims, current profile protection, and available test inputs. Do not promise autonomous play merely because a shell or a UI-related skill is listed. Do not ask Howie to provide a save as the first response to missing automation.

## Authorized fixture route

The agent is authorized to create a **new disposable test fixture**, including through a fresh Beneath the Stolen Lands game if installed and suitable. It does not have to reproduce historical save bytes or the old Mammoth pair.

A useful minimum is:

- A supported rider with a genuine KMC Horse, able to mount, carrying an ordinary melee weapon and shield. Retain the relevant Mounted Combat/Shield Focus/Mounted Shield setup for regression observation if practical.
- A safe place to save unmounted and idle, and a nearby accessible melee encounter with room to approach and at least one target that survives long enough to observe a bite/hoof sequence.
- The ability to switch RT/TB through the game's normal interface and obtain fresh eligible paired activations. An extra unmounted melee actor or an equivalent separate control is useful for timing comparison; it is not a reason to build a large fixture campaign.
- A non-Horse control with legitimate trip when that regression needs native confirmation. Reuse an existing admissible stock control where available; do not delay the whole alpha to build every optional control in one save.

Use actual game UI and legal character creation when tools allow. An existing approved diagnostic setup may create controlled unit/equipment states if its protections and provenance permit it; label it diagnostic, and do not count it as native character-creation/feat-selection UI acceptance. Do not hand-edit a .zks file to pretend the game created it or reuse another project's save without actual authorization and compatibility evidence.

For a new fixture, preserve an immutable game-generated seed/master and derive separate run-scoped working copies. Record the seed/working hashes, path ownership, creation steps, game/UMM/mod versions, character/horse identities, conditions/equipment, and exact working copy used in each observation. No special historical hash value is required by this mission.

If an old script requires old qualification records, keep that guard intact. Use a supported isolated-save route or a narrowly reviewed new admission path that actually validates the new fixture. Do not rename the new save to spoof admission, copy old qualification receipts, override expected hashes, or relax a historical scenario and reclassify its old result. A general fixture/automation framework is outside scope.

## Runtime protection

Follow current repository guarded deployment/launch rules, ownership claims, previews, identity gates, and source/safety review before a real run. Protect and restore **actual current** UMM `Params.xml`, profiles, installed Mods/settings/caches and relevant save roots. Never restore an old historical preview as the current user's state. Finish restoration on success and on failure.

The prior alpha report identified a no-save `mod-load-smoke` route that lacked complete UMM settings/profile snapshot and restoration. Treat that exact route as inadmissible until its current implementation is verified safe; lack of a save is not evidence of lack of persistent effects. If reusing `sprint6-shield-rt` or `sprint6-shield-tb`, retain their current required `-BaseGameOnly` protection. Do not broaden the new mission into general old-runner rehabilitation.

Respect existing game/runtime locks even when another session uses a separate game executable: user profile, Steam, saves and global settings can still be shared. Do not interrupt a human session, bypass a lock, change foreign mods, hot-replace a DLL, or kill unrelated processes. Stop on authentication, entitlement, purchase, update or unexpected cloud dialogs.

## Time and review bounds

- Set `KMC_WORKFLOW_BUDGET_ID=mounted-alpha2-melee-pose-20261124` in each validation shell. Read and preserve its actual spend and all project/global constraints.
- Allow at most 30 minutes active fixture/setup work plus 10 minutes focused smoke/cold-load work, at most three guarded game starts, within the remaining cumulative validation allowance. These are ceilings, not targets or extensions.
- Group the useful observations into one declared small batch, at most five distinct cases under repository policy. Stop earlier if safe tools/admission are absent, or after an equivalent failed attempt unless a concrete new observation changes the experiment.
- Obtain the required independent review of the actual production/safety change before live use only when a concrete safe route is available. Use `PRE_NATIVE_REVIEW.md`; one focused review and at most one correction/targeted recheck for this optional route. An unresolved safety concern blocks that run.
- Never interrupt active saving or restoration to meet a timer. Record actual elapsed time honestly.

If blocked, record the exact missing capability or safeguard and the candidate/rows affected. Continue source, focused checks, package preparation and formal alpha review where allowed. Do not manufacture a pass, renew a budget, reset formal rounds, or tell the owner that supplying a vanished historical save is the only possible way forward.

## Evidence from any real batch

Capture exact loaded binary and fixture provenance, input/actor/target and current paired phase, relevant movement/attack states, and visible outcome. Reuse diagnostic counters and structured native rule traces; add only the missing narrow event fields needed to distinguish the candidate causes.

Use short ordinary-game observations for movement and animation. Do not force dice outside 1–20, clear action debts, speed up turns, or synthesize attacks to make a demo pass. A directed test harness must distinguish its own setup from native behavior. For RT responsiveness, separate time to start movement from time to execute the first attack.

Retain the original evidence and reader version/result, include cancellation/failure/restoration outcomes, and mark only actually observed rows as verified. A successful launch or main-menu load is startup evidence; it does not close mounted melee, animation, or save/load acceptance.
